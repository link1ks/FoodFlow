# 食光社区

登录后可从「社区」进入，个人厨房无需创建家庭即可使用。社区是全站分享空间，显示作者昵称，不显示联系方式和家庭库存。

## 分享与发现

配方必须包含标题、人数、预计耗时、1–3 个标签、目录食材及精确用量、完整步骤。可上传 JPG/PNG 封面；浏览器会缩小图片，服务端重新编码为 JPEG，去除照片元信息。没有封面时显示标明用途的食材示意图。提交前需明确同意将配方文字及封面发送至审核模型，并同意通过后公开分享及署名收录。

可搜索、筛选、点赞、收藏，查看自己的配方。每人每天最多提交两道新配方；相同作者不能重复发布相同食材、份数及步骤的配方。通过后保持固定版本，可撤下后另发改进版。撤下会清除封面；已经审核入库的食谱版本继续保留。

## 配方与封面初审

新动态先进入「待初审」，在「我的配方」显示进度。Worker 在后台调用结构化审核模型，检查配方完整性、食材与步骤合理性、明显危险做法、广告导流和明显不适合公开的内容。有封面时同时发送图片，检查可辨认内容、图片内文字及明显广告/隐私信息；模型必须返回图片已检查，才可通过。

通过后才进入公共动态、允许点赞收藏、参加周榜并获得发布积分。未通过显示修改建议，可以修改文字、替换或移除封面，重新确认后提交。修改时未上传新图会保留原封面并重新审核；已通过或正在审核的版本不能直接修改。模型未配置、额度不足、响应格式无效或服务失败时显示「审核暂不可用」，保留内容，仅作者及社区管理员可访问详情和封面。没有自动放行或未配置模型的规则兜底。旧动态维持原有可见性，不标注为已完成模型初审。

专用审核模型配置是完整的一组，不能混用服务商密钥：

```dotenv
COMMUNITY_REVIEW_MODEL_ENDPOINT=https://your-provider.example/v1
COMMUNITY_REVIEW_MODEL_NAME=your-vision-capable-model
COMMUNITY_REVIEW_MODEL_API_KEY=configure-locally
AI_ALLOWANCE_ENABLED=true
```

这些值只放在本机配置，不提交 Git。模型需支持 Chat Completions、图片输入和 JSON 输出。未设置任何专用值时，无封面使用现有 `MODEL_*`，有封面使用 `VISION_MODEL_*`；只填部分专用值会停止审核，不会借用另一服务的密钥。配置后重建 API/Worker。真实调用可能收费，请确认服务商价格及 `AI_*` 额度后再启用；默认不自动开启收费模型。

社区审核与菜单模型共用服务总额度、每日次数及并发锁，每个动态版本只有一次自动派发记录。网络结果不明时保留预留额度，Worker 重启不会自动重复收费调用；需运营人员向服务商核实后处理 `community_review_calls` 的不确定记录。作者手动修改重交会产生新版本和新调用，仍受总额度限制。额度是应用侧上限，不是服务商账单。隔离验收专用的本地模型仅按虚构测试标题返回预定结果，不用于真实审核。

## 每周精选

- 北京时间周一 00:00 至下周一 00:00，统计首次点赞发生在该周且仍有效的赞。不允许给自己的配方点赞；取消后再次点赞不会变成新一周的赞。
- 每周最多三道候选，每位作者最多一席。按票数降序，同票按发布时间、配方 ID 排序。已经入库或已撤下的动态不参与。
- Worker 启动及每小时结算上一完整周，票数与席位结算后固定。停机漏掉的更早周，可由社区管理员调用 `POST /api/community/weeks/YYYY-MM-DD/finalize` 补结算。
- 管理员审核食材、用量、做法以及每步设备与耗时；当前排餐专注模式只支持案板和灶台。审核通过才写入食谱库，并保留作者署名。未通过需说明原因。

## 积分和装饰

| 贡献 | 积分 | 限制 |
| --- | --- | --- |
| 新配方初审通过 | +5 | 每天最多一次；按通过日计算 |
| 收到其他用户的首次点赞 | +1 | 每天最多 20 分；重复点赞不重复奖励 |
| 配方审核入库 | +50 | 每道配方只奖励一次 |

积分可兑换新芽创作者徽章（30）、暖阳头像框（80）、蜜糖社区主题（120）。兑换后立即启用；已拥有的奖励不会重复扣分。积分用于社区装饰，不兑换现金或实物。取消点赞、撤下动态不追回已发积分，也不会重发。积分账本只追加；授予、余额检查、兑换与请求回放在同一事务内完成。

## 配置社区管理员

家庭管理员与社区管理员是不同权限。默认没有社区管理员，普通用户无法通过请求参数获取审核权限。

1. 用准备作为管理员的账号登录，在浏览器开发者工具查看 `GET /api/community/account` 响应中的 `user_id`。它是 UUID，不是邮箱或昵称。
2. 在本机 `.env` 中设置 `COMMUNITY_ADMIN_IDS=用户UUID`，多个 UUID 用逗号分隔。不要提交 `.env`。
3. `docker compose up -d --build api worker`；学习部署使用其专用环境文件和 Compose 参数。配置生效后，「每周精选」显示审核操作。

Compose 开发、学习及验收配置均支持这个变量。社区操作要求登录及 `Idempotency-Key`；所有写入使用独立的社区事务锁，不改变库存写入和家庭授权。封面储存在 PostgreSQL，迁移 033 增加社区表，035 增加初审状态、版本租约及调用记录；数据库备份应包含这些表。

## 当前边界

这是初期社区功能：没有评论、关注、通知、举报工单或自动刷票检测。每天发布与积分上限、自赞限制、每作者一席只能减少部分滥用，不能识别多账号刷票；管理员可撤下不适合的动态。模型初审可能漏判或误判，不保证食品安全，也不代替周榜人工入库审核。正式开放前仍需要补充举报处理、真实模型准确度评估、运营审核及负载验证。社区内容是用户分享，份量和耗时为估计，实际烹饪需确认熟透。

积分和装饰当前归各自账号所有。现有邮箱/手机号账号合并会保留来源账号的作者历史，但暂不会把它的社区配方管理权、收藏、积分和装饰转入目标账号；使用社区后请优先保持同一个账号。
