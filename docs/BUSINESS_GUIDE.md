# 业务上下文与更新指南

本指南保存当前业务含义；历史执行计划保存当时发生的事实，不把历史试验改写成当前验收结果。
机器入口为 [business.json](quality/business.json)：每个需求都有上下文、实现来源、测试、浏览器复核、数据规模与未验证范围。
测试映射以命名用例为单位，Go 子测试、fuzz seeds 和表格数据继承父用例。绑定说明验证目的，运行报告才说明是否通过。

## 数据规模与二次验证

每个需求在映射中说明代表性数据和边界；无需对密码哈希或格式校验盲目运行百万条数据。每次完整验证至少执行现有的 10 家庭、20 并发客户端、30 秒混合负载，至少 100 个完成周期/700 个请求；检查越权、幂等重放、精确余额、流水与 Outbox 守恒，错误与不变量失败为零，p95 不超过 2000 ms。此门槛属于本地有界回归，不宣称生产容量。

业务页面二次验证在 15173 的虚构账号中按关联场景运行，每个场景同时覆盖桌面与手机。默认主站 5173 另开全新无登录浏览器，只读检查首页、就绪状态及实际 JS/CSS 构建，保存无账号截图。单元测试无法在首页逐条重演；不得把首页 HTTP 200 冒充已验证全部业务操作。

## 每次更新必须执行

1. 把本次每条用户要求写入任务契约，关联业务 ID 与命名测试；开始任务后绑定契约，禁止结束时删除未满足条件。
2. 阅读对应业务指南、源码、API/数据库契约与历史风险。修改任何关联源码或指南后，复核本表与 business.json 的上下文、测试、数据规模和限制。
3. 补充复现和回归，审查业务含义后运行 `go run ./cmd/harness -mode business -update`。该命令记录已审查输入摘要，不替代人工语义判断；禁止只为消除红灯而刷新。
4. 执行 full、acceptance、diagnose、main-site；有应用更新时先按原部署备份和重建，再做主站验证。验收环境运行与全量数据库测试顺序执行，避免内存争抢。
5. 提交并同步 main，等待该提交云端 CI 成功，运行 cloud；用全部证据提交任务完成门禁。失败保留实际记录并补回归，不降低断言或编造成功。

真实模型效果、物理麦克风、短信送达、真实用户研究和生产容量仍遵守 [质量台账](QUALITY.md)，本指南不宣称这些已验收。
