# FoodFlow 项目与 Harness Engineering 评估

日期：2026-10-01（Asia/Shanghai）。任务：`project-audit-20261001`。

## 范围与判断

检查产品说明、架构、业务实现、测试、harness 源码、隔离验收脚本、交付记录与当前提交的云端验证。只新增评估文档，不修改业务行为、模型配置或开发数据。没有授权或执行付费模型调用。

FoodFlow v0.2.0 已具备可运行、可演示、可持续迭代的 MVP 主流程：库存 → 菜单草案 → 用户确认 → 采购 → 入库 → 烹饪扣库 → 历史记录。当前交付不等于生产上线完成，也没有一个已约定、足以计算整体完成百分比的产品 backlog。

已经可以称为实施了 harness engineering：仓库导航、可执行架构约束、生成知识、确定性测试、真实隔离验收、脱敏运行反馈、任务完成门禁与提交关联的 CI 证据形成了开发反馈链。该判断参考 [OpenAI 的工程案例](https://openai.com/index/harness-engineering/)，不是认证或行业统一成熟度等级，也不证明持续自治开发或 AI 效率收益。

## 优化顺序与可验证完成条件

以下是建议 backlog，不代表本次已经实施或授权上线。

1. **补强 API 契约门禁。** `internal/app/openapi_test.go` 当前只解析 YAML、检查版本字段及至少 25 个 path。`knowledge` 会检查路由清单变化，但不会证明 OpenAPI 的请求/响应与实现一致；不少响应只有文字描述。先增加标准 OpenAPI 校验、API 路由与方法对照，补全主流程响应 schema，再对真实 fixture 响应做契约检查，逐步生成前端类型。完成条件：删除路由、改变必填字段或把数量从字符串改为数字时，对应检查明确失败。
2. **补齐浏览器成功链路。** 目前 3 个场景在 desktop/mobile 各执行一次，共 6 项；包括真实登录/导航、网关错误、连续入库/能力状态/确认交互。部分准备与菜单确认经 API 完成，烹饪确认用例允许 200 或 409，所以它验证确认边界，不能独立证明浏览器成功扣库。API smoke 已验证成功消耗。新增用 UI 完成的库存充足路径、采购入库、确认菜单、成功烹饪后余额和流水断言，以及成员降权/家庭切换。完成条件：主流程 UI 按钮接错接口、成功后数据不刷新、重复点击重复扣库时，回归失败。
3. **建立按业务域的质量与技术债台账。** CI 已产出 coverage，但未见按域维护的质量评分、关键场景映射或增长趋势；任务统计目前是运行次数、结果与墙钟时间。记录各域负责人、验收标准、未覆盖风险和关闭证据；持续统计失败类别、返工和用户回归，区分基础设施/fixture/产品失败。对核心数量与分配算法增加属性测试或 fuzz，验证守恒、非负、单位隔离。完成条件：任何主要功能可追溯至需求、场景、证据及遗留限制；不以重复绿色运行证明生产质量或效率提升。
4. **扩展架构与代码卫生规则。** 直接 import 的有限黑名单可漏过其他来源的 I/O 依赖；`internal/app/app.go` 约 596 个非空行、`plans.go` 约 708 个，`IngredientCatalogPicker.tsx` 约 512 个、`Week.tsx` 约 448 个，适合作为按职责拆分的候选，非自动判定缺陷。优先覆盖允许的依赖方向、禁止间接绕过及 SQL 服务所有权；接入前端 lint/format 检查，对新增长的大文件做有基线的预算。完成条件：每条新增规则有接受合法代码与拒绝违规代码的回归，不进行无业务收益的大规模重写。
5. **加强镜像证据与环境可复现性。** acceptance 的 `-skip-build` 只复用当前镜像，没有自动比较 image ID、构建 revision 与 source digest；源码稳定不证明容器运行的是同一代码。记录容器 image ID、构建摘要、Compose 配置摘要和浏览器版本，复用时校验绑定，避免错误镜像通过旧行为验收。检查环境隔离由 denylist 走向明确的测试配置；本次没有证据表明发生了外部调用泄漏。完成条件：使用旧镜像或不匹配构建摘要会明确失败，报告可以说明每个运行对象对应的代码。
6. **上线前形成运维验收。** 在目标部署环境验证 HTTPS、密钥管理、内部访问控制与所采用的 Redis/Kafka 认证加密配置；先按规模决定是否启用平台扩展及复制，不为小规模试用强行拆更多服务。补持续 HTTP 错误率/延迟、outbox 最老积压、Worker 过期租约、Kafka lag 与 quarantine 告警，加入安全的 request/job/event 关联标识。演练厨房/图片/Insights 的备份恢复、投影重建、发布回滚和消费者重平衡，运行多家庭持续混合读写。完成条件：定义负载、SLO、RPO/RTO 后实测达标；目前约 0.10–0.75 秒的 GET 压测不作容量依据。
7. **补 AI 和真实家庭价值评估。** 建立脱敏/合成的冰箱、偏好、排除食材、未知单位和模糊照片样本；默认使用确定性 fixture，检查非法结构与越权方案拒绝。真实模型评测必须另行授权预算、模型版本与样本，统计识别正确率、建议接受/修改率、延迟与成本。随后进行小规模家庭试用，测首次使用成功率、录入负担、采购/烹饪闭环与回访。真实短信、S3、公网部署、浪费金额/长图导出、换绑/合并/短信找回仍属未交付或未验收范围；按实际需求排期。

建议先完成 1–3，再依据“作品展示、家庭试用或公网服务”的目标安排后续；当前核心事务架构适合继续保留。
