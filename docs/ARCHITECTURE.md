# 架构与设计边界

厨房核心采用模块化单体 API + Worker，Redis 为必需的公共读取缓存；可选平台扩展增加 Kafka 库存事件和拥有独立数据库的 Insights 微服务。API 必须配置并连接 Redis 后才能启动，就绪检查同时检查 PostgreSQL 与 Redis。服务所有权、事件交付与恢复边界见 [PLATFORM](PLATFORM.md)，可执行工程约束见 [HARNESS](HARNESS.md)。

```text
React + TanStack Query ──HTTP/SSE──> Gin API ──pgx/sqlc──> PostgreSQL
                                      │                  ↑
                                      └─ jobs 表 ──> 独立 Worker
                                                   ├─ 菜谱/库存/偏好只读工具
                                                   └─ Eino 消息结构 + 模型适配器
```

**家庭权限。** 新会话使用 HS256 JWT，严格校验算法、签发方、受众与有效期，再结合数据库令牌哈希实现退出撤销；家庭权限不写死在 JWT 中。API 通过会话查用户，家庭路由统一查询 `members`。Agent Worker 在使用家庭偏好、库存与菜谱前，再以任务创建者身份检查成员角色。模型不接收数据库连接、SQL 或命令执行能力。邀请令牌只存哈希，且绑定受邀邮箱。

离线恢复码需当前密码再验证及明确确认后生成，数据库仅保存随机 128-bit 码的哈希、180 天有效期和凭证版本。恢复锁定用户，单次证明、新密码、版本递增、全部会话撤销与剩余恢复码失效共享事务；短信重置、换号及合并更新凭证版本也拒绝旧恢复码。未预存码且无有效短信证明时不提供邮箱知识式重置。

收费模型还需显式开启 AI 预扣保护。每次 HTTP 请求前，在 PostgreSQL 全服务锁下验证权限/租约、同任务唯一性、月度家庭与服务共同额度、每日次数和跨月并发，提交精确整数预扣。费用不确定时保留预扣与并发，不自动退款或再次发送；管理员核查后只释放并发，不减少预扣。适配器仅接收 guard 回调，不拥有数据库。预扣额度限制不等同于服务商账单封顶，价格与真实用量验收仍属开放债务。

**库存。** `batches` 保留批次余额，`stock_ledger` 通过触发器禁止更新和删除。扣减使用事务内批次行锁、条件更新和非负约束。纠正是新流水。采购项目的 `stocked` 标志、计划的 `consumed` 状态和家庭范围内的幂等键共同阻止不同键重复入库或消耗。幂等表同时保存请求摘要与响应，相同键换内容返回 409。
v1.1 将日期有效期固定解释为家庭时区的该日结束，并保存 `expires_at`；自动烹饪只领取状态正常、未过期的批次，按到期时刻、购买日期、创建时间排序（FEFO，同到期日 FIFO）。`meal_completions` 对家庭＋日期＋餐次建立唯一约束。逐餐完成、批次出库流水与安全线补货项在同一事务提交；系统补货清单独立于菜单采购清单。用户修改批次实际余量时提供预期余额，过期写入返回 409。未设置期限且有余量的正常批次按临期提醒展示，明确标注未设期限；提醒不写入虚构到期日、不认定已经过期，也不改变 FEFO 的未知期限排序或自动扣库规则。
删除食材采用软归档：先锁定食材与批次，将剩余余额归零并写入 `ref_type=ingredient_archive` 的补偿流水，再设置 `archived_at`。普通库存、规划、提醒和照片读取不再返回归档条目；再次入库同一规范名称和单位会清除归档标记，历史流水仍保留。

**食材图片与菜谱探索。** 图片对象经存储接口写到本地共享卷或 S3，数据库只存对象键、MIME 与版本；访问图片必须先通过家庭成员权限。更换图片使用新对象键和数据库行锁，提交后再清理旧对象。用户勾选库存食材后，服务端以“所选食材 → 菜谱需求”的依赖图计算可做状态与缺口，并按就绪程度、缺少种类、匹配数量和耗时排序。菜谱之间没有先后依赖，因此这里是依赖满足排序而非严格的拓扑排序。需求计算沿用精确数量和维度换算规则，遇到不可换算单位不输出精确缺口。创建菜单仍是草案，确认和消耗各自重新校验实际库存。
v1.1 的 `internal/engine/matcher` 将原料键离散为多字位集，使用 `math/bits` 计算缺料种类；菜谱 BOM 新增目录 ID，已有规范食材按目录 ID 匹配，非目录食材以名称回退。热路径输入是预编译索引和选中位集，不调用数据库。`internal/engine/scheduler` 将有效批次按到期时间建小顶堆，按人数缩放 BOM，以共享原料余额作排他分配，使用乐观上界剪枝搜索多菜组合。组合读取 API 在家庭权限校验后获取库存快照；结果不预留库存，也不代替烹饪事务的锁定与复核。组合搜索最多 20 道候选、默认 20 万节点，达到预算会标示截断。`plan_meals` 保存每餐主菜，`plan_meal_dishes` 保存附加菜；确认和烹饪时统一汇总 BOM，共享原料不足则事务回滚。

附近价格只读取 market_benchmark_prices。保留来源、城市、原品名、规格和监测周期，仅北京时间当天的日监测记录算今日价。internal/market 提供全国 36 城市月报及北京、苏州、福州日报同步器，cmd/price-sync 手动运行，Worker 可每 6 小时同步；每个数据源独立事务，单源失败不阻止其他源更新；唯一键保证重复导入不增加样本，缺失值不估算。HTML 解析展开肉类表头 colspan，严格校验城市行与单位；月报起止日期来自正文，不使用下载时间。5 升油价用精确有理数折算每升，最终四舍五入到两位小数。API 不同步抓取外部网页；家庭成员鉴权仍保留。社区成交接口和前端已删除，旧表仅归档保留。

价格按同城市、同来源、同原品名、规格、单位和监测日期保存；保留原文链接。周同比只匹配同口径、起止日期均相差 7 天的记录，缺失为 null。前端每 30 秒重新读取数据库，图文卡片明确标明日价日期或月均年月。全国报告不得拆成虚构的每日记录，不向其他城市复制价格。

**食材目录。** 公共只读目录由数据库迁移提供分类、规范名称、默认单位和别名。前端全屏选择界面默认展示全部图文卡片，Trie 索引优先返回名称与别名前缀匹配，再补充包含匹配；分类、计量维度和家庭库存过滤在候选结果上执行。200 种目录食材使用本地 AI 生成的写实棚拍风参考图，统一为 480×360 浅奶油白画布；生成提示、源图摘要和裁切记录随资产保存，图片说明明确其为生成参考图。家庭已有照片优先显示，图片失效或非目录食材显示“暂无参考图”。家庭照片绑定当前家庭与图片版本，并在切换时撤销旧对象 URL。目录选择与批次入库在同一个幂等事务中完成，服务端用目录 ID 查名称、分类和单位，忽略客户端对这些字段的伪造值。旧的自由名称接口仍保留给已有调用方和图片识别确认流程；目录可随迁移扩充，现有家庭库存不会被重命名。

**Redis。** 食材目录、公共菜谱列表和官方价格查询正式使用 Redis，缓存有效期最多 60 秒；菜谱和价格键区分完整筛选条件，价格键另含上海日期，避免跨日复用“今日价”判断。缓存读取仍在会话和必要的家庭权限校验之后。仅缓存完整成功结果；连接使用短时限且不重试，运行时故障回源 PostgreSQL。公共数据更新允许一个 TTL 内的延迟。缓存可丢弃重建，无需纳入业务备份；库存、权限、会话撤销、幂等、收费调用保护及 Worker 租约仍由 PostgreSQL 持久保存。

**菜单。** 生成任务仅创建草案。服务端按菜谱份数计算需求并将可兼容单位归一到 g/ml 或相同计数单位；不兼容单位显式标记。家庭与单次规划的明确忌口食材按菜谱食材名称匹配，生成候选时排除，确认时再次检查。确认还检查修订版本并重新计算采购缺口；做饭消耗时再次检查库存。采购清单的“已买”和“已入库”是两个独立状态。

**Worker。** `FOR UPDATE SKIP LOCKED` 领取队列；租约每 12 秒续期，过期后可被其他 Worker 领取。完成事务必须匹配租约令牌且任务未取消，旧 Worker 因而无法覆盖新结果。演示模式的读取和计算可有限重试；配置真实模型时，可能产生费用的请求失败或租约过期不会自动重试。模型服务没有 exactly-once 保证。`job_events` 保存进度和错误，确认/拒绝后更新任务终态。

**实时同步。** `business_events` 由数据库触发器记录家庭变更，API 通过 SSE 发送 `sync`；任务事件也由 SSE 发送。前端重连后会重新查询 API，数据库为最终事实来源。当前实现每 2 秒查询事件表，适用于个人/家庭规模；若负载增长，可改 PostgreSQL LISTEN/NOTIFY 辅助唤醒，但仍以事件表补偿断线。

**模型边界。** 一个任务最多一次模型调用、最多二十个候选菜谱。菜单规划必须返回已给出的 `recipe_id`；营养建议返回受限长度的摘要、提示及已知 `recipe_ids`，数量由服务端计算。模型仅选方案；数量和单位由确定性 Go 代码计算。演示模式选固定排序第一道符合耗时的菜谱，并在任务详情显示 `mode: demo`。没有把外部菜谱文本提升为系统指令。

**图片识别。** API 校验文件大小和实际格式后写入本地共享卷或 S3 兼容存储，再排队执行 `image` 任务。Worker 在读取对象和调用视觉模型前重新检查任务创建者权限。视觉模型输出为 scene 与 foods；只接受真实照片中唯一一种且能唯一匹配当前目录的食材，分类由目录填写，确认时再次校验。数量、单位、日期由用户核对输入。确认接口在家庭权限检查下，使用幂等键与任务行锁，在同一事务中创建批次、追加库存流水并完成任务。取消待确认任务不会写库存。视觉模型调用可能收费，因此图片任务不自动重试。

## 账号与短信

统一登录按 account 识别手机号或邮箱，通过对应用户记录校验密码，不会按相同密码合并用户。绑定手机号须当前会话、当前密码和绑定用途的短信验证码三者校验；手机号唯一约束防止占用其他账号。旧未验证手机号只能先用密码登录，验证后才开放短信登录。

短信发送通过 Sender 接口与阿里云 RPC 适配器实现。挑战保存 HMAC、用途、用户、失效时间和尝试次数，不保存明文验证码。发送前在事务中预占全局、IP、手机号预算；外部发送只调用一次，失败或不确定结果不自动重试。验证码消费与注册或绑定写入共用事务，错误猜测单独提交计数。发送成功仅表示供应商接受请求，不能视为运营商已送达；短信真实送达尚未验证。

## 最近交互与数据边界

采购项删除设置 deleted_at，不删库存流水；编辑与入库均排除已删除条目，补货唯一索引只覆盖未入库且未删除的记录。取消任务在前端淡出收起，数据库任务与事件保留。个人中心归集个人资料和手机号绑定；头像为昵称首字展示，尚无个人照片上传。

营养资料嵌入 Go 包：200 种食材有说明，198 种具备可追溯参考值，泛指鱼与贝类保留未知；每100克参考值不自动转换成整餐摄入。营养建议读取所选家庭库存快照，并受任务租约、取消与成员权限约束。采用建议才建立菜单草案，生成建议不扣库存。

## 代码边界与部署验收

食光社区由 API 管理全站登录用户的配方版本、点赞收藏、候选审核与追加式积分账本。食材来自公共目录，用量统一为精确目录单位；社区写入使用独立事务锁，不取得家庭库存锁。新版本需明确同意文字及封面发送至审核模型；Worker 以有界租约在数据库事务外调用模型，严格校验结构化结果。只有初审通过或历史公开内容可被非作者互动、排行及收录；失败保持私有，作者可修改后确认重交。每版本唯一派发记录与菜单任务共用服务额度锁，结果不明保留占额，不自动重复派发；过期租约、已撤下或旧版本的结果不能恢复公开。审批可见性及发布积分同事务提交。Worker 按北京时间自然周结算候选，只有明确配置的社区管理员能审核入库，并确认每步设备和耗时。家庭管理员不自动拥有全站审核权限。积分与兑换、请求回放同事务提交，撤下动态保留已经收录的食谱版本。模型初审不代替人工入库审核或实际烹饪安全确认。具体规则见 [食光社区](COMMUNITY.md)。

个人厨房是默认入口，家庭共享可选。迁移 034 区分个人/家庭空间并保存默认个人厨房映射；显式 PUT 在用户行锁内幂等创建。私有空间成员查询还校验实际所有者，禁止邀请、加入和改成员角色。既有家庭和库存不迁移，账号合并保留来源的私有厨房与历史；目标已有默认空间时保持其默认。详见 [个人厨房](PERSONAL_KITCHENS.md)。

前端 `main.tsx` 负责挂载，`app/AppShell.tsx` 负责个人厨房入口与导航，`pages/` 按库存、菜单、任务与设置拆分；共享查询和类型位于 `app/shared.tsx`，不额外建立客户端服务端状态副本。

烹饪服务 `cooking_service.go` 与调味品服务 `pantry_service.go` 接收 `context.Context`、调用方事务和显式家庭/操作者作用域；HTTP Handler 负责鉴权与参数解析，幂等包装控制提交。服务不自行提交事务，确保库存、流水、餐次状态与补货写入共享回滚边界。其余历史 Handler 仍在逐步整理，当前保持模块化单体。

API 支持 SIGTERM 最多 10 秒优雅退出；SSE 无全局写超时，关闭期限届满后终止剩余连接。独立验收 Compose 使用专属数据库和图片卷、随机密钥与本机端口，复现脚本与验证范围见 `docs/LOCAL_DEPLOYMENT.md` 和 `docs/VERIFICATION.md`。
